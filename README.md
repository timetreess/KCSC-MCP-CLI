# KCSC Standards MCP/CLI

> AI가 건설기준을 추측하지 않고, 근거로 답하게 만드는 도구.

KCSC Standards MCP/CLI는 국가건설기준센터(KCSC)의 `KDS`, `KCS`, 전문시방서 정보를 AI 에이전트가 직접 찾아보게 해주는 MCP/CLI 도구입니다.

Claude Desktop, Cursor, opencode 같은 에이전트에 이 레포를 붙여두면, AI가 “아마 이런 기준일 겁니다”라고 말하기 전에 KCSC OpenAPI에서 기준 후보, 원문 조항, 개정 metadata, 출처 URL을 먼저 확인하게 만들 수 있습니다.

저는 토목 분야에서 설계사 경험도 있고, 시공사에서 근무하는 실무자로서 기준 때문에 시간을 많이 써봤습니다. 보고서 문장 하나에 근거 기준을 붙여야 할 때, 발주처 검토의견에 답해야 할 때, KDS와 KCS를 같이 봐야 할 때, AI가 만들어낸 기준번호가 진짜인지 확인해야 할 때가 있습니다.

이 프로젝트는 개발자가 상상한 검색기가 아니라, 실제 토목 업무에서 자주 겪는 “기준 근거 찾기” 문제를 줄이기 위해 만든 도구입니다.

---

## 일단 추가하면 뭐가 좋아지나요?

이 레포를 MCP로 추가하면, 사용자는 복잡한 명령어를 외울 필요가 없습니다. 평소처럼 AI에게 물어보면 됩니다.

> “터널 방수 기준 찾아줘.”  
> “되메우기 다짐 기준 원문 근거 찾아줘.”  
> “이 보고서에 들어간 KDS/KCS 인용이 실제 있는 기준인지 검토해줘.”  
> “이 내용이 설계기준 쪽인지 시방서 쪽인지 나눠서 봐줘.”

그러면 에이전트는 뒤에서 KCSC 기준 검색, 원문 조회, 조항 근거 확인, 인용 검증을 수행합니다.

핵심은 이것입니다.

- 기준번호를 몰라도 관련 `KDS`, `KCS`, 전문시방서 후보를 찾을 수 있습니다.
- 설계기준과 표준시방서를 같은 주제로 나란히 확인할 수 있습니다.
- AI가 만든 그럴듯한 기준 인용을 그대로 믿지 않고 검증할 수 있습니다.
- 검토의견이나 질의회신에 붙일 기준명, 조항, 원문 일부, 출처 URL을 빠르게 모을 수 있습니다.
- “최신 metadata에 있음”과 “이 프로젝트 계약상 적용됨”을 구분하게 만들 수 있습니다.

## 실무에서 특히 쓸모 있는 순간

### 1. 발주처 검토의견에 “근거 기준 제시”가 달려왔을 때

설계보고서나 구조계산서 검토 중 이런 코멘트를 자주 받습니다.

> “되메우기 다짐 기준 근거 제시 바람.”  
> “교좌장치 설치 기준 확인 필요.”  
> “터널 방수 관련 설계기준과 시방기준을 구분하여 제시.”

이때 담당자는 예전 보고서, 표준시방서 PDF, KCSC 검색창, 사내 자료를 왔다 갔다 하게 됩니다. 이 도구를 붙여두면 AI에게 바로 “관련 KDS/KCS 후보와 원문 근거를 찾아서 정리해줘”라고 시킬 수 있습니다.

### 2. KDS와 KCS가 머릿속에서 섞일 때

설계사는 설계기준을 봐야 하는데, 실제 문장 작성이나 시방서 검토에서는 KCS 근거도 같이 필요합니다. 문제는 같은 주제라도 KDS와 KCS의 표현과 위치가 다르다는 점입니다.

이 도구는 같은 주제에 대해 설계기준과 표준시방서를 함께 찾는 흐름을 지원합니다. “설계 판단 근거는 KDS에서, 시공 요구사항은 KCS에서”처럼 AI가 기준의 역할을 나눠 보게 만들 수 있습니다.

### 3. AI가 써준 기준번호가 진짜인지 불안할 때

AI에게 보고서 문장이나 검토의견 초안을 맡기면, 문장은 그럴듯한데 기준번호가 틀릴 수 있습니다. 존재하지 않는 KDS/KCS 코드를 만들거나, 비슷한 분야의 기준을 잘못 끌어올 수 있습니다.

이 레포의 인용 검증 기능은 문서 안의 KDS/KCS 코드를 뽑아 실제 KCSC metadata에 존재하는지 확인하는 용도로 쓸 수 있습니다. AI를 더 많이 쓰기 위해서가 아니라, AI가 만든 결과를 더 안전하게 쓰기 위한 장치입니다.

### 4. 제안서 마감 직전에 “기준 근거”를 붙여야 할 때

기술제안서, VE 검토, 대안공법 설명에서는 문장보다 근거가 중요할 때가 많습니다. “이 공법은 관련 기준에 부합한다”라고 쓰려면 최소한 어떤 기준을 봤는지, 원문 근거가 있는지 확인해야 합니다.

이 도구는 최종 문장을 대신 써주는 것보다, 제안서에 붙일 수 있는 기준 후보와 근거 조각을 빠르게 모으는 데 초점을 둡니다.

### 5. 신입이나 타 공종 담당자가 기준 위치를 물어볼 때

실무에서는 “그 기준 어디에 있나요?”라는 질문이 자주 나옵니다. 매번 선임자가 기억으로 답하거나 검색해서 링크를 던져주는 대신, 에이전트에게 기준 후보와 출처를 찾게 할 수 있습니다.

## 설치는 AI 에이전트에게 맡기세요

이 README를 읽는 사람이 직접 터미널 명령어를 따라 칠 필요는 없습니다. 아래 문장만 본인이 쓰는 코딩 에이전트에게 붙여넣으세요.

> 이 레포를 내 환경에 설치하고 MCP로 연결해줘: https://github.com/timetreess/kds  
> KCSC API 키는 내가 발급받아 넣을 테니, 실제 키가 GitHub나 커밋에 들어가지 않게 설정해줘.  
> 설치가 끝나면 KCSC 기준 검색이 되는지 간단히 확인해줘.

에이전트가 알아서 확인해야 할 내용은 다음 정도입니다.

- npm 패키지 이름은 `kcsc-standards-mcp`입니다.
- MCP 서버 이름은 보통 `kcsc-standards`로 두면 됩니다.
- API 키 환경변수 이름은 `KCSC_API_KEY`입니다.
- 실제 API 키는 공개 저장소, README, issue, commit message에 남기면 안 됩니다.

## KCSC API 키는 어떻게 준비하나요?

이 도구를 쓰려면 KCSC OpenAPI 인증키가 필요합니다. 키 발급은 한 번만 준비하면 되고, 이후에는 AI 에이전트가 로컬 설정에 연결해주면 됩니다.

방법은 다음과 같습니다.

1. 국가건설기준센터 api 사이트에 접속합니다: www.kcsc.re.kr/support/api
2. 회원가입 후 로그인합니다.
3. '인증키 발급신청' → '발급신청'을 클릭합니다.
4. 발급받은 키를 복사해 둡니다.
5. 코딩 에이전트에게 “이 키를 내 로컬 MCP 설정의 `KCSC_API_KEY`로 넣어줘. 저장소에는 커밋하지 마.”라고 시키면 됩니다.

KCSC 사이트 메뉴나 신청 방식은 바뀔 수 있습니다. 막히면 에이전트에게 “KCSC OpenAPI 키 발급 위치를 공식 사이트에서 찾아줘”라고 시키세요.

## AI가 뒤에서 할 수 있는 일

사람은 자연어로 물어보고, AI는 아래 기능을 도구로 사용합니다.

| 하고 싶은 일 | AI가 뒤에서 하는 일 |
|---|---|
| 관련 기준 찾기 | KDS, KCS, 전문시방서 metadata 검색 |
| 설계기준과 시방서 같이 보기 | 같은 주제의 KDS/KCS 병렬 검색 |
| 기준 원문 확인 | 기준 코드로 KCSC 원문 섹션 조회 |
| 조항 근거 찾기 | 원문에서 관련 조항과 문장 찾기 |
| 기준번호 검증 | 문서 안의 KDS/KCS 인용 존재 여부 확인 |
| 적용성 참고 | 프로젝트/공종 기준으로 참고용 관련성 판단 |

## 출력에서 중요하게 보는 것

이 프로젝트는 “멋진 답변”보다 “검증 가능한 근거”를 우선합니다. 가능하면 AI가 다음 정보를 함께 보여주도록 설계했습니다.

- 기준유형
- 기준코드
- 기준명
- 조항번호 또는 섹션 경로
- 개정일 또는 metadata update date
- 원문 일부
- 적용성 판단
- 신뢰도
- 출처 URL

신뢰도는 다음처럼 구분합니다.

- `원문 직접 근거`: 기준 원문 본문이 확인됨
- `관련 조항 추론`: 직접 문구는 아니지만 관련 조항이 확인됨
- `근거 미확인`: 현재 조회 범위에서 근거를 확인하지 못함

### 근거 정보의 완전성

- `원문 직접 근거`는 실제 본문과 함께 기준명, 개정일 또는 metadata update date까지 확인된 경우에만 표시합니다. 이 값이 빠지면 `관련 조항 추론`으로 낮추고, 빠진 항목을 `evidenceGaps`로 함께 알려줍니다.
- API 응답에 기준명이 없을 때 기준코드 문자열로 채워 넣지 않고, 그 사실을 `미확인 근거 정보`로 표시합니다.
- 원문 HTML을 단순 텍스트로 바꿀 때 위첨자는 `^`, 아래첨자는 `_`로 보존하고, 이미지는 `alt`가 있으면 `[그림: 설명]`, 없으면 `[그림]`으로 남깁니다. 원본 HTML은 `sections[].html`에 그대로 유지됩니다.
- `kcsc get`은 조항을 임의로 잘라내지 않고 전체 조항을 출력하며, 조항 수를 함께 표시합니다.

### 조회 실패와 부분 결과

- API 응답 형식 오류는 빈 검색 결과나 기준 미존재로 처리하지 않고 오류로 알립니다. 일부 metadata나 문서 항목이 잘못된 경우에도 조용히 제외하지 않습니다.
- 조항 검색에서 모든 후보의 상세 조회가 실패하면 CLI는 실패 종료하고 MCP는 도구 오류를 반환합니다.
- 일부 후보만 조회에 실패하면 성공한 결과와 실패 기준 목록을 함께 제공합니다. MCP `find_clause`의 `failures`가 비어 있지 않으면 불완전한 검색이며, `clauses`가 비어 있어도 전체 후보에 근거가 없다는 뜻이 아닙니다.
- CLI는 부분 결과의 본문에 경고를 표시하고 실패 내역은 stderr에 출력합니다. 일부 조회가 성공한 부분 결과의 종료 코드는 0입니다.
- 라이브러리의 `ClauseFinder.findClause()`는 기존 배열 반환을 유지하지만 부분 실패 시 오류를 냅니다. 부분 결과가 필요한 호출자는 `findClauseWithDiagnostics()`의 `{ clauses, failures }`를 사용합니다.

## 꼭 알아야 할 한계

이 도구는 토목 실무자의 판단을 대체하지 않습니다. 특히 다음은 반드시 구분해야 합니다.

- KCSC metadata에 존재한다고 해서 해당 프로젝트 계약상 반드시 적용되는 것은 아닙니다.
- 적용성 판단은 참고용입니다. 계약문서, 특기시방서, 발주처 요구사항, 현장 조건, 인허가, 전문기술자 검토가 우선합니다.
- 현재 KCSC OpenAPI가 과거 기준문서 본문 비교를 제공하지 않으므로, 개정 전후 본문 비교 도구는 아닙니다.
- 검색 결과가 없다는 것은 “기준이 없다”는 뜻이 아니라, 현재 검색 범위에서 직접 근거를 찾지 못했다는 뜻입니다.
